## 2. ВВЕДЕНИЕ

Объектом тестирования является приложение «В Хосписе» («V Hospice») v.1.0.0 для Android (**сборка из предоставленного исходного кода**).

Приложение даёт функционал по работе с новостями хосписа и включает в себя:

* Информацию о новостях и функционал для работы с ними;
* Тематические цитаты.

## 3. ЦЕЛИ ТЕСТИРОВАНИЯ

1. Определение реализованного функционала на текущем этапе разработки.
2. Проверка работоспособности основных сценариев пользователя (создание, чтение, редактирование новостей).
3. Выявление дефектов UI/UX при различных конфигурациях устройств.
4. Создание набора автоматизированных UI-тестов для регрессионной проверки.

## 4. ОБЪЕМ ТЕСТИРОВАНИЯ

### 4.1 В область тестирования входит:

* **Авторизация:** Вход по предоставленным данным (`login2/password2`), выход из аккаунта.
* **Главная страница:** Отображение блока "Новости", переход к полному списку.
* **Раздел «Новости»:**
  * Просмотр списка и деталей новости.
  * Сортировка и фильтрация.
  * Публикация новой новости.
  * Редактирование существующей новости.
  * Удаление новости.
* **Раздел «Тематические цитаты»:** Раскрытие/свертывание текста.
* **Глобальная навигация:**
  - Открытие и работа **Navigation Drawer** (через иконку ≡).
  - Корректная обработка системной кнопки **«Назад»** (включая закрытие Drawer без выхода из приложения).
  - Поведение **AppBar** (верхней панели): скрытие/появление при скролле, отображение заголовков текущего экрана.

### 4.2 В область тестирования не входит:

* Кроссплатформенное тестирование (iOS).
* Тестирование серверной части (Backend).
* Нагрузочное тестирование.
* Push-уведомления.

### 5.1 Объекты тестирования:

* APK-файл / Сборка Gradle.
* Мобильный интерфейс (Activity/Fragment).
* Backend-логика через публичные эндпоинты REST API (анализ ответов и контрактов).

### 5.2 Функции для тестирования:

* Аутентификация и управление сессией.
* CRUD-операции со списком новостей (валидация полей: пустые значения, спецсимволы).
* Механизмы сортировки (по дате) и фильтрации.
* **Глобальная навигация:** работа Drawer-меню, переключение табов AppBar, системная кнопка «Назад».
* **Статический контент:** «Тематические цитаты» (сворачивание/открытие блоков).

## 6. ПОДХОД К ТЕСТИРОВАНИЮ

### 6.1 Типы тестирования

* **Функциональное тестирование**
  * **Позитивные сценарии:** Проверка работоспособности основных функций при вводе корректных данных (успешная авторизация `login2/password2`, создание новости с валидными полями, переход по ссылкам).
  * **Негативные сценарии:** Проверка обработки ошибок и устойчивости системы (попытка входа с пустыми полями, создание новости без заголовка, фильтрация новостей по несуществующей категории, нажатие кнопки «Назад» на экране Splash Screen).
* **Юзабилити-тестирование (UX/UI) и Доступность (Accessibility)**
  * **Удобство использования:** Оценка интуитивности навигации между экранами через Drawer-меню; проверка читаемости шрифтов.
  * **Доступность (*A11y*):** Проверка работы приложения со включенными сервисами TalkBack (VoiceOver); верификация контрастности текста при темной теме согласно стандартам WCAG; проверка адаптации интерфейса под системный масштаб элементов (`Font Size`).
* **Конфигурационное тестирование**
  * **Ориентация экрана:** Корректное отображение всех элементов UI (без перекрытий, выходов за границы или обрезания текста) при смене портретного режима на альбомный и обратно.
  * **Темы оформления:** Правильное инвертирование цветов (темный фон / светлый текст) при переключении Dark Mode в системе Android.
  * **Масштабирование:** Сохранение целостности верстки при увеличении и уменьшении масштаба дисплея в настройках устройства.
  * **Локализация:** Корректное отображение текстов при смене языка системы (если ресурсы локализации присутствуют), отсутствие "хардкода" строк в коде.
* **Исследовательское тестирование (Exploratory Testing)**
  * Свободный поиск дефектов вне рамок написанных чек-листов: попытки вызвать краши путем быстрой смены экранов ("Rage Taps"), одновременного выполнения действий, ввода спецсимволов из буфера обмена и проверки граничных значений полей.
* **Автоматизированное тестирование**
  * **UI-автоматизация (Espresso/JUnit4):** Написание сценариев для регрессионной проверки критического функционала. Проверка наличия элементов на экране после переходов.
  * **API-автоматизация (через MockWebServer/Postman):** Валидация структуры JSON-ответов сервера (наличие обязательных полей, типов данных, HTTP-статусов) без запуска графического интерфейса эмулятора. Использование статичных Fixture-файлов для имитации ответов Backend-а.

### 6.2 Уровни тестирования:

Системное (End-to-End).

### 6.3 Методы тестирования:

* **Серый ящик (*Grey-box*):** проектирование тестов на основе анализа пользовательского интерфейса с использованием знаний внутренней архитектуры приложения (доступ к исходному коду через Android Studio) для настройки стабильных ожиданий (*Idling Resources*) и поиска элементов (*ViewMatcher*).
* **Негативное тестирование:** проверка устойчивости системы при вводе невалидных данных, нарушении последовательности действий и эмуляции ошибок сервера/сети.

### 6.4 Инструменты:

* **IDE:** Android Studio.
* **Сборка:** Gradle, JDK 17 (`JAVA_HOME`: `ms-17.0.18`).
* **Тестирование:**
  * **UI-автоматизация:** Espresso, JUnit4, Allure Report.
  * **Библиотеки:** Allure Java, Hilt Testing.
  * **Анализ API:**
    * **Android Studio Logcat** — перехват исходящих HTTP-запросов в реальном времени для определения эндпоинтов и структуры тел запросов.
    * **Postman** — воспроизведение API-вызовов вручную, проверка корректности JSON-схем ответов и сохранение коллекции запросов как эталонной документации.
* **ОС хоста:** Windows 11 Pro.

## 15. НЕПРЕДВИДЕННЫЕ ОБСТОЯТЕЛЬСТВА

При возникновении критических ошибок сборки (`Gradle Sync Failed`) или запуска APK, связанных с конфликтом транзитивных зависимостей (часто встречается при использовании Firebase BOM + Hilt):

1. Выполнить очистку кэша IDE и Gradle (`File -> Invalidate Caches / ./gradlew clean --refresh-dependencies`).
2. Проверить дерево зависимостей командой `./gradlew :app:dependencies` на предмет дубликатов версий библиотек.
3. Если падение вызвано ошибками Desugar (конвертация Java 8+ функций для старых API), проверить версию библиотеки `desugar_jdk_libs`.
4. Если автоматизация конкретного экрана невозможна из-за сложности внедрения моков в Hilt Graph, выполнить проверку данного модуля вручную и задокументировать ограничение автотестов в отчете Allure.
